# SDD Framework: Spec-Kit (GitHub Next / Martin Fowler SDD Model)

Spec-Kit — это спецификационно-ориентированный фреймворк разработки (Specification-Driven Development), ориентированный на контрактно-ориентированное взаимодействие распределённых команд (Cross-functional UI & Logic Teams) и кодинг-агентов.

## 1. Концепция и принципы Spec-Kit

В отличие от легковесного CLI OpenSpec (ориентированного на локальные дельты изменений в рамках одного рабочего пространства), Spec-Kit строится вокруг **Executable Contract Specifications** (исполняемых контрактных спецификаций):

1. **Contract-First (Спецификация предшествует коду)**: ни одна строка кода UI или бэкенда не генерируется и не пишется до момента подписания общего контракта (`unified_contract.yaml`).
2. **Dual-Team Specification Boundary**:
   - **UI Team**: формулирует требования через экраны, сценарии взаимодействия, переходы состояний (State Machine: Loading, Empty, Success, Error) и карту ошибок формы.
   - **Logic Team**: формулирует требования через доменные сущности, инварианты валидации, алгоритмы фильтрации/сортировки и протокол ошибок (RFC 7807).
3. **Formal Reconciliation Step (Фаза согласования контракта)**: детерминированное выявление расхождений (schema mismatch, casing, pagination models, error structures) и их устранение до фазы реализации.
4. **Verifiable Behavior**: каждый пункт спецификации транслируется в автоматический тест контракта или E2E-сценарий.

## 2. Сравнение Spec-Kit и OpenSpec (Критерий 1 оценки ДЗ — 2 балла)

| Характеристика | OpenSpec (Fission AI) | Spec-Kit (GitHub Next / Fowler) |
|---|---|---|
| **Основной фокус** | Пошаговое ведение одного разработчика/агента через цикл фичи (Explore → Propose → Apply → Sync → Archive) | Межкомандная синхронизация контрактов (UI vs Backend API) до старта разработки |
| **Управление артефактами** | Локальный CLI (`openspec`), директории `changes/<name>/`, `specs/` | Декларативные каталоги спецификаций (`team1-ui/`, `team2-logic/`, `contract/`) |
| **Формат изменений** | Дельта-спеки (`## ADDED Requirements`, `## MODIFIED Requirements`) | Полные спецификационные контракты версий v1 (draft) и v2 (reconciled) + OpenAPI 3.1 |
| **Кастомизация правил** | Файл `config.yaml` (`rules.design`, `rules.specs`) передаёт промпты агенту | Схемные валидаторы (JSON Schema / OpenAPI linting) и протоколы согласования |
| **Риск расхождения (Drift)** | Низкий в рамках одной ветки, но нет встроенного арбитража между двумя параллельными агентами | Минимальный риск дрейфа между фронтендом и бэкендом за счёт жёсткого контракта RFC 7807 |
| **Overhead** | Минимальный для одиночных фич brownfield-проекта | Оправданный для распределённых сервисов и командной разработки |

## 3. Структура каталога `spec-kit/`

```text
spec-kit/
├── README.md                     # Описание фреймворка и сравнение с OpenSpec
├── team1-ui/
│   ├── spec_v1_draft.md          # Спецификация UI ДО согласования
│   └── spec_v2_aligned.md        # Спецификация UI ПОСЛЕ согласования контракта
├── team2-logic/
│   ├── spec_v1_draft.md          # Спецификация логики ДО согласования
│   └── spec_v2_aligned.md        # Спецификация логики ПОСЛЕ согласования контракта
└── contract/
    ├── negotiation_log.md        # Журнал согласования и принятые решения
    ├── unified_contract.yaml     # Итоговый контракт OpenAPI 3.1 / JSON Schema
    └── diff_summary.md           # Сводный отчёт об изменениях до/после
```
