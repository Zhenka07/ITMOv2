Часть 2 · Настройка OpenSpec

Кастомизация правил и diff до/после

Добавление проектного правила в openspec/config.yaml и верификация инструкций:

rules:
  design:
    - "Обязательно объясни архитектурное взаимодействие компонентов диаграммой Mermaid."
  specs:
    - "Формулируй все приёмочные сценарии строго в нотации Given/When/Then (####)."
ДО правила (Слабый текст):

Client issues mutation request -> Server handler receives request -> Server checks validation -> Server executes storage update -> Server calls audit journal logger -> Audit logger appends record -> Server sends HTTP response.

ПОСЛЕ правила (Диаграмма Mermaid):

Формальный sequence-диаграммный контракт взаимодействия: Client ⇄ Server ⇄ Validator ⇄ ItemStore ⇄ AuditJournal с ветвлением ошибок 400 Problem Details.

Архитектурный контракт

Диаграмма взаимодействия (Mermaid Sequence)

Сгенерирована агентом согласно новому правилу проекта для фичи audit-logging:

sequenceDiagram autonumber actor Client as Client / Dashboard participant Server as HTTP Server (server.py) participant Validator as Validator (models.py) participant Store as ItemStore (storage.py) participant Audit as Audit Journal (audit.py) Client->>Server: POST /api/v1/items (Mutation) Server->>Validator: validate_item_input(data) alt Validation Error Validator-->>Server: ValidationError (invalid_params) Server-->>Client: 400 Problem Details (RFC 7807) else Validation Success Validator-->>Server: Clean Data Server->>Store: create(data) Store-->>Server: Created Item Server->>Audit: record_event(item.created) Audit-->>Server: OK Server-->>Client: 201 Created Item end
ДЗ 5 · Эмуляция двух команд

Две команды — одна фича (Spec-Kit)

Эмуляция параллельной работы UI-команды и Logic-команды с раздельными контекстами:

КОМАНДА 1: Frontend UI

- Экраны, верстка, интерактивные фильтры и чипы.
- Стейт-машина: LOADING, SUCCESS, EMPTY, ERROR.
- Форма модалки и подсветка невалидных полей.
- Кнопки прямого скачивания JSON / CSV экспорта.

КОМАНДА 2: Backend Logic

- Доменная сущность Item, типы, инварианты валидации.
- Алгоритм фильтрации, поиска и пагинации.
- Стандартизированный протокол ошибок RFC 7807.
- Потоковый синхронный экспорт и журнал аудита.

Каждая команда составила независимую спецификацию spec_v1_draft.md ДО начала какого-либо кодинга.

Единый контракт

OpenAPI 3.1 & RFC 7807 Problem Details

Итоговый арбитраж оформлен в машиночитаемом контракте spec-kit/contract/unified_contract.yaml:

openapi: 3.1.0
paths:
  /api/v1/items:
    get:
      parameters: [category, status, search, sort_by, sort_order, offset, limit]
      responses:
        '200':
          headers:
            X-Total-Count: { type: integer }
          content:
            application/json: { schema: { $ref: '#/components/schemas/ItemListResponse' } }
        '400':
          content:
            application/problem+json: { schema: { $ref: '#/components/schemas/ProblemDetails' } }
  /api/v1/items/export:
    post:
      requestBody: { content: { application/json: { schema: { $ref: '#/components/schemas/ExportRequest' } } } }
      responses:
        '200': { content: { application/json: {}, text/csv: {} } }
Реализация

Работающая система: Console UI & REST API

Web UI Console (SPA)

- Поиск с debounce (250ms), фильтры по категориям и статусам.
- Карточки статистики KPI (Всего, Active, Pending, Archived).
- Модалка создания с подсветкой ошибок конкретных полей.
- Кнопки скачивания JSON и CSV файлов через Blob API.

REST API & Data Storage

- Thread-safe хранилище ItemStore с JSON-синхронизацией.
- Стриминг RFC 4180 CSV с экранированием запятых и кавычек.
- Строгая схема RFC 7807 для всех ошибок (400, 404, 409).
- Журнал аудита с автозаписью событий при мутациях.

Доступно локально по адресу: http://localhost:8080/ (запуск через make run).

Интеграция

Собственный MCP-сервер DataHub Inspector

Интеграция кодинг-агентов через Model Context Protocol (JSON-RPC 2.0 stdio):

1. list_items

Фильтрация, сортировка и пагинация по критериям.

2. get_item

Чтение детального объекта по уникальному ID.

3. create_item

Создание сущности с валидацией по контракту.

4. update_status

Мутация жизненного цикла (active/pending/archived).

5. export_items

Синхронный экспорт в JSON или CSV формат.

6. get_audit

Чтение журнала аудита для security-контроля.

Аналитика

Сравнение: OpenSpec vs Spec-Kit

Критерий OpenSpec (Fission AI) Spec-Kit (Fowler / GitHub Next)
Главная цель Управление локальной дельтой одного разработчика/агента Межкомандный арбитраж контрактов (UI vs Logic)
Формат артефактов Дельта-спеки (## ADDED / MODIFIED) Версионированные спеки (v1 draft → v2 aligned + OpenAPI 3.1)
Управление дрейфом Правила в config.yaml и детерминированный CLI Машиночитаемая валидация по JSON Schema контракту
Накладные расходы Минимальные для одиночных фич Оправданы при распределенной разработке
Итоги и Рефлексия

Ключевые выводы практики

Что доказала практика:
  • SDD — не Waterfall 2.0, если итерации компактны (Small Batches).
  • Согласование контракта до кода предотвращает дорогостоящий рефакторинг.
  • Инъекция правил (Mermaid) радикально повышает читаемость документации.
  • RFC 7807 превращает ошибки в структурированный интерфейс для фронтенда.
Роль человека:
  • Ограничение дрейфа LLM (отсечение лишних сложностей вроде async очередей).
  • Принятие архитектурных компромиссов (offset/limit vs cursor).
  • Финальная приёмка и валидация реального поведения сервиса.
