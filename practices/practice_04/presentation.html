5. Устройство собственного MCP: URL Inspector

Для бота реализован сервер mcp-url-inspector/server.py на базе стандартного протокола Model Context Protocol (MCP) через JSON-RPC 2.0 поверх stdio. Сервер написан на чистом Python 3 без внешних библиотек (zero-dependency: urllib, html.parser, json, sys).

Как MCP взаимодействует со средой:
  1. initialize — клиент и сервер согласуют версию протокола и возможности (capabilities).
  2. tools/list — сервер экспортирует JSON-схему инструмента inspect_url с описанием и типами аргументов.
  3. tools/call — модель генерирует вызов функции, сервер выполняет сетевой запрос и возвращает структурированный ответ.

Регистрация в opencode.json:

{
  "mcp": {
    "servers": {
      "url-inspector": {
        "type": "local",
        "command": "python3",
        "args": ["mcp-url-inspector/server.py"],
        "disabled": false
      }
    }
  }
}

6. MCP Tool: Успешный вызов и обработка ошибок

Инструмент inspect_url никогда не падает с аварийным исключением. Он обрабатывает все типы некорректного входа и возвращает понятную структурированную ошибку (isError: true).

1. Успешный сценарий (Valid URL ➔ 200 OK + Title):

>> CLIENT REQUEST (tools/call):
{
  "name": "inspect_url",
  "arguments": { "url": "https://example.com" }
}
<< SERVER RESPONSE:
{
  "status": "success",
  "reachable": true,
  "status_code": 200,
  "content_type": "text/html",
  "title": "Example Domain",
  "final_url": "https://example.com"
} (isError: false)

2. Обработка ошибочного входа:

  • Неподдерживаемая схема (ftp://): возвращает error_type: "UNSUPPORTED_SCHEME".
  • Запрещенный хост (127.0.0.1 / localhost): защита от SSRF возвращает error_type: "FORBIDDEN_HOST".
  • Несуществующий домен / таймаут: перехват DNS и таймаута без падения процесса сервера.
>> CLIENT REQUEST: {"name": "inspect_url", "arguments": {"url": "http://127.0.0.1:8080/admin"}}
<< SERVER RESPONSE:
{
  "status": "error",
  "error_type": "FORBIDDEN_HOST",
  "message": "Host '127.0.0.1' is not allowed for security reasons"
} (isError: true)

8. Рефлексия по практике (reflection.md)

1. Что помогло:

  • TDD-скилл: Пошаговая методология Red-Green-Refactor заставила четко сформулировать граничные условия до написания логики валидации.
  • Собственный MCP url-inspector: Вынесение сетевой проверки веб-страниц в отдельный MCP-сервер позволило протестировать инструмент изолированно. Обработка запрещенных локальных адресов localhost, неверных схем, таймаутов показали устойчивость — сервер не крашится, а возвращает структурированную ошибку.
  • Изоляция в Git Worktree и Subagent Review: Реализация фичи B в отдельном каталоге дала полную уверенность, что стабильная фича A не повреждена. Субагент подтвердил отсутствие регрессий и обратил внимание на общий бюджет таймаута для последовательных операций.

2. Что мешало и вызвало сложности:

  • CGO и SQLite: Драйвер go-sqlite3 требует включенного CGO. При запуске тестов и сборки агенту было критично явно помнить про CGO_ENABLED=1, что было закреплено в AGENTS.md.

3. Где потребовалось вмешательство человека (Human-in-the-Loop):

  • Проектирование поведения при сбое в SendRandom: В фиче B при выдаче ссылки выполняются два действия: отправка сообщения в Telegram и удаление ссылки из базы. Возник вопрос: что делать, если сообщение успешно ушло пользователю, но база вернула ошибку при удалении? Было принято решение: не возвращать ошибку выше, а записать предупреждение в лог.
