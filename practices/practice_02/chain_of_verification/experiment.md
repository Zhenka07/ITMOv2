# Chain of Verification

- Проверяемый черновик или утверждение:
  Утверждения из черновиков `analysis.md` и `project_management.md`:
  1. «Проверка длины diff > 20000 символов может выполняться внутри LLM-клиента или возвращать ошибку 422».
  2. «При сбоях и таймаутах LLM клиенту возвращается 500 с описанием ошибки».
  3. «Для отладки в лог сервиса выводится начало diff и ответ LLM».

## Запрос на проверку

```text
Вы — AI-аудитор технической документации. Работайте строго по технике Chain of Verification (CoV):
1. Сформулируйте 4 проверочных вопроса к утверждениям черновика.
2. Проверьте каждое утверждение по правилам CASE.md и коду TRAINING_PR.diff.
3. Отклоните любые неподтвержденные утверждения и галлюцинации.
4. Верните исправленный результат с явными ссылками на строки evidence.
Скрытые рассуждения модели исключите.
```

## Вопросы проверки и evidence

| Вопрос | Источник или проверка | Результат |

| Где и с каким кодом отклоняется diff длиннее 20000 символов? | `CASE.md:65`, правило `API-1` | Отклоняется строго на уровне API с HTTP 413 Payload Too Large (не 422 и не внутри LLM). |

## Исправленный результат

```markdown
В конвейере TO BE:
1. Запрос проверяется Pydantic-моделью (422 при невалидном теле).
2. Длина diff валидируется до бизнес-логики: > 20000 символов -> HTTP 413 (API-1).
3. До обращения к LLM выполняется sanitize(diff) -> токены заменяются на [REDACTED] (SEC-1).
4. Вызов LLM ограничен таймаутом 10с, сбои превращаются в контролируемый ответ HTTP 502/504 (REL-1).
5. Логирование строго ограничено request_id, длительностью и статусом; тело diff и ответа не логируется (OBS-1).
```
